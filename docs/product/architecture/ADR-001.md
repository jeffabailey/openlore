# 001 A resumed scan takes over its plan row statuses
Status: Proposed

## Context

```text
A scan freezes its plan before its first read (ADR-088) and the store counts, for the owner latest run alone, the plan rows whose status is read (fix-repos-read-truthful). Each resume starts a new run and kept only the rows still planned, so after a budget pause that read one of three repos and a resume that read the other two, the queue said two repos read. The owner decided on 2026-11-21 that the count is of the whole scan and that the resuming run takes over the reads the paused run already saved.
```

## Decision

```text
A resuming run records the whole frozen plan it resumes as its own plan, minus the rows skipped, each row carrying the status it already holds: a row read stays read, a row still planned stays planned. ScanRunPort record_plan therefore takes plan rows with their status, in one transaction. The count stays what it was: the rows of the latest run whose status is read.
```

## Alternatives

```text
A scan-chain identifier linking a resuming run to the run it resumes, with the count taken over every run of the chain. Rejected: it needs a stored schema change with its migration, and the count must then be of distinct repos to avoid counting a repo read twice across two runs, where one row per plan gives that for nothing. One run for the whole scan, a resume picking the paused run identity up instead of starting a new one, which would need no copy at all. Rejected: it changes what a run is for every reader of it, the start time, the summary of account checks and the per-run counts of a scan paused for hours, and the owner decided instead that the resumed run takes the earlier reads over. Leaving the count per run and changing the words of the line. Rejected: the owner asked for the whole-scan count, and the words are out of scope.
```

## Consequences

```text
The queue accounts for the whole scan across any number of resumes, and a repo whose earlier read was never saved still counts once. A plan row already read is carried even when its source was removed meanwhile, because the scan did read it; nothing more is read for that source. A run whose plan write is refused reports no count and stays resumable, and if it also wrote no row, the next scan plans afresh and starts a new count. No schema change and no migration.
```
